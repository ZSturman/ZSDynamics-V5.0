# November 22, 2026 report: what each observation means

Source: a read-only dry run of the daily report against the live GA4 property on November 23, 2026 (`gh workflow run daily-analytics.yml -f dry_run=true`, run 45250105526), plus code inspection. GA4 only provides aggregates for that day, so some questions can only be narrowed down, not settled. Each item says which.

| # | Observation | Status | Explanation and change |
| --- | --- | --- | --- |
| 1 | 10 Better Workspace "GitHub" clicks vs 3 detail-page views | **Instrumentation defect (fixed); exact split still to query** | `ResourceButton` also renders in the project-card icon strips (`/projects` grid and list) and the same repository is linked from `/better-workspace`. Every click was logged with `surface=project_resource`, so card clicks were indistinguishable from detail-page clicks. Clicks also inherited the section of **whichever element was last visible**, which is why all 10 were labelled "View Source". California, served by 6 San Jose sessions (1 engaged), produced 11 of the day's 17 resource clicks, so several clicks came from a few sessions. Fixed: clicks now carry the clicked element's own `surface` (`project_grid`, `project_list`, `selected_work`, `project_modal`, `project_page`, `product_page`…), `source_section` and `destination_category`, and the leaky "last visible section" context was removed. To settle Nov 22 itself, run `gh workflow run analytics-verify.yml -f days=3` and read **Resource clicks by project and page** and **Resource clicks by hour, city and project**. The daily report now does the same split every day and explains mismatches. |
| 2 | 49 of 49 sessions `(direct) / (none)` | **Unresolved; no defect found** | Nothing in the site strips referrers. UTM parameters have stayed in the landing URL since October 27, and GA4 reads `document.referrer` itself. Automated deep links send no referrer, and shares from messaging apps, email clients and many mobile apps don't either, so "direct" fits the rest of the day's evidence (see 3–5) but proves nothing. The session stream records the landing `ref_host` independently, and the brief compares the two. If the stream sees referrers that GA4 reports as direct, that points to a GA4 attribution problem worth investigating. |
| 3 | 21 sessions from Council Bluffs, Iowa (a large Google Cloud region), 16 of them "engaged", 2 actions | **Not classified** | Location is never used to classify a session. The engaged share is high and actions are low, which fits browsers that stay open for more than 10 s, but the aggregates cannot show which sessions those were. The brief mentions concentrations like this as context only. |
| 4 | 25 GA4-engaged sessions but only 4 with a `user_engagement` event | **Expected GA4 behaviour** | A session is "engaged" after 10 s in the foreground, two page views or a key event. gtag sends `user_engagement` mainly when a page is hidden, unloaded or changed, and otherwise attaches engagement time to other events. Browsers shut down without a visibility change (typical for automation), or sessions that end through a key event, can be engaged without one. The gap is supporting evidence of automated or abruptly ended sessions, not a measurement bug. The report now explains this and no longer presents `user_engagement` sessions as an engagement count. |
| 5 | 13 desktop route views with a "tablet" window | **Terminology; supporting evidence** | `viewport_category` measures window width (768–1023 px = "tablet"), while GA4's `deviceCategory` comes from the user agent. Common automation tools open 800×600 windows by default. The report now labels this "window width class". The session stream records an exact-800×600 bit as classification evidence, never on its own. |
| 6 | Product activity unavailable; `product_slug`, `action_type` missing | **Configuration** | 35 of 50 event-scoped custom-dimension slots are used. `product_id`, `product_slug`, `action_type`, `log_id`, `filter_type`, `filter_value` and `qa_run` are not registered. The reporting service account cannot register them. See "Register custom dimensions" below. The misleading warning that listed `eventName` as missing now lists only the dimensions that are actually missing. |
| 7 | "Visitor Journeys" section | **Misleading label (fixed)** | It listed aggregate `entry → page` route-event counts, not paths. It is now called **Aggregate Route Transitions**, and observed paths come only from the session stream. |
| 8 | Page views (54) vs route views (51–58) | **Expected** | GA4 `page_view` fires on loads and history changes. `portfolio_route_view` fires on pathname or project-modal changes and is de-duplicated by route key. They measure different things and are no longer compared as if they were the same. |
| 9 | "+563% engagement rate", "+3,400% engaged sessions" | **Presentation (fixed)** | Percentages on small baselines exaggerate. The brief shows absolute changes and percentage points (for example `+43 pp vs Sat`) and drops percentages below a baseline of 5. |

## Register custom dimensions (owner action)

GA4 Admin → Data display → Custom definitions → Create custom dimension, **scope: Event**, for each parameter:

`product_slug`, `action_type`, `destination_category`, `source_section`, `filter_type`, `filter_value`

That uses 6 more slots (41 of 50). Do not register `product_id`, `log_id`, `destination_url` or labels; see [event-taxonomy.md](./event-taxonomy.md#ga4-custom-dimensions). Registered dimensions only apply to data collected afterwards. `analytics-verify.yml` prints which recommended dimensions are still missing.
